\section{Threat model}\label{sec:threats}

\subsection{Assets}

\begin{itemize}
  \item \textbf{The principal's money and accounts} at relying parties, which agents act on.
  \item \textbf{The PA issuer key} and \textbf{task keys}: whoever holds them can create valid agent identities or requests.
  \item \textbf{Relying parties' trust} in the KYA signal: if forged requests pass verification, the whole scheme loses its value.
  \item \textbf{The audit history}: the basis for investigations and accountability.
  \item \textbf{Cluster resources and model budget}, which runaway agents consume.
\end{itemize}

\subsection{Trust assumptions}

We assume the following components are \emph{trusted} and correctly deployed: the Kubernetes control plane, Agent Substrate's isolation (gVisor or microVM), \code{ax-server}, \code{ax-controller}, and our own admission proxy, passport authority, signing proxy, observer and ledger. We also trust AX to enforce each task's \code{Gateway} egress policy. We assume the university OIDC provider authenticates people correctly. Standard cryptography (Ed25519, SHA-256, TLS~1.3) is assumed to be secure.

We assume nothing about the \emph{agent}: its code, its model, its inputs and everything else inside the sandbox may be malicious at any time.

\subsection{Residual risks and limitations}\label{sec:residual}

We state openly what the design does \emph{not} solve:

\begin{itemize}
  \item \textbf{Misuse within the mandate.} If the visa allows ordering up to 500~TRY at a shop, a hijacked agent can still place a bad order for 480~TRY. KYA bounds the \emph{blast radius}; it does not guarantee that every in-scope action matches the principal's intent. Tight visas, low approval thresholds and the observer reduce, but do not remove, this risk.
  \item \textbf{Exfiltration through allowed channels.} An agent allowed to post reviews could hide stolen data in a review text. Content inspection is out of scope.
  \item \textbf{Relying parties that do not verify.} The signature only helps services that check it. For others, the signing proxy's allowlist and metering still apply.
  \item \textbf{Trusted signing proxy.} Because it terminates TLS and holds task keys, a compromised signing proxy is a serious incident. We mitigate with a minimal code base, keys in memory only, short passport lifetimes and separate deployment; hardware-backed key storage is future work.
  \item \textbf{Egress enforcement depends on the platform.} If AX's gateway does not restrict sandbox egress to the signing proxy reliably (Section~\ref{sec:seams}), a malicious agent could bypass the proxy. Continuous gateway reconciliation is still on the AX roadmap. The evaluation reports which mode was used.
  \item \textbf{A secret AX places in the sandbox.} AX's workspace setup agents need a model API key inside the container~\cite{ax-sandbox}. A compromised agent could read it and use it through the signing proxy, where it is metered and attributed, but it could also leak it through an allowed host. Moving this key out of the sandbox depends on AX (separate setup actor, on its roadmap) or on credential injection in the signing proxy (stretch goal).
  \item \textbf{A moving upstream target.} AX is pre-1.0. Calls we depend on (\code{UpdateTask}, \code{SuspendTask}, the runner contract, the \code{Gateway} resource) may change. We pin one AX version and keep AX-specific code in thin adapters (Section~\ref{sec:plan}).
  \item \textbf{False positives.} An over-eager observer can suspend legitimate agents. Suspension (rather than deletion) keeps this recoverable; tuning is part of the evaluation.
\end{itemize}
